# Science Labs library

## Navigation

The Vite build has four entry points, including the supplementary `activity.html` activity. `index.html` hosts the catalog; `lab.html` hosts the existing osmosis investigation; `investigation.html?lab=:id` hosts the modular investigations. Hash routes work on static hosting and GitHub Pages repository subpaths without server rewrite rules:

- `#/` — landing page
- `#/science` — discipline selection
- `#/science/biology` — eight Biology units
- `#/science/biology/:unitId` — unit investigations
- `#/science/biology/:unitId/:labId` — lab overview
- `#/search?q=...&available=1` — shareable search results

All catalog pages have global search and breadcrumbs. The working lab has return navigation and library search. The service worker caches all HTML entries and the PDF resources, including offline navigation. The existing lab retains its `cell-lab` browser-storage key so previously saved experiments remain usable on the same origin.

## Content

`src/catalog.js` contains eight units and 48 main Biology investigations organized alongside Biology 2e chapters. All 48 are locally runnable. The 33 previously planned builds each passed their separate development review; see BIOLOGY_BUILD_TASKS.md and the evidence records. These new labs are marked Virtual only and include completed PDF download, native print and matching student/teacher materials. The optional Sordaria extension and matter-cycle activity are also runnable. Classroom/virtual input modes are defined per activity. Local availability and development acceptance are separate from production publication, classroom/device acceptance, standards approval and reviewed translations.

Records have stable IDs, subject/unit relationships, type, version, status, supported modes, and launch URL. Add another lab or interactive by adding a record and its standalone entry point; register the entry with Vite. Add subject-level routes when another discipline has real content. Current search indexes lab titles, summaries, units, subjects, and chapter references. Search is browser-side and needs no service.

## Standalone progress and account-platform boundary

Content IDs remain separate from teacher, assignment, learner, and attempt IDs. Platform assignments reference a lab ID and immutable release. Reports retain activity responses and data provenance (measured, simulated, or supplied). Future automatic assessment will need explicit activity-level evidence definitions and rubric versions; completion is not a grade.

The standalone library uses browser localStorage as temporary device progress. Its optional name fields do not authenticate a student. The separate account platform implements real authentication, server authorization, cloud drafts, immutable submissions, and teacher feedback/scores; see the account-platform section below. Automatic grading is not implemented.

## Production and development deployments

`main` publishes at `/Science_Labs/`. `codex/development` publishes at `/Science_Labs/dev/`. A push to either branch rebuilds and tests both branches, assembles a single Pages artifact, and verifies progress/cache isolation in Chromium before publishing. Keep the workflow on both branches in sync. Both branches must be allowed in the `github-pages` environment. Never deploy a single branch artifact by itself: Pages replaces the entire published site.

Each address exposes `deployment.json` with the branch and deployed SHA. Preview pages display a testing banner and use a distinct browser-storage key. Service worker caches are namespaced by their registration path; root workers ignore `/dev/` traffic. The legacy production `cell-lab` progress key remains unchanged. This is operational separation on one origin, not a security boundary for untrusted code.

To promote the reviewed library, merge `codex/development` into `main`. Development edits stay on `codex/development` until that promotion. GitHub Pages preview is public.

## Virtual-only genetic information lab

`genetic-information` is a supplemental Genetics catalog entry (`virtualOnly: true`, modes `[Virtual]`), with its own `genetics-app.js`, model, artwork, report builder and scoped styles. It does not replace the stable extraction or reporter-expression routes. Catalog totals are derived from entries.

The six stages distinguish orientation, DNA replication, transcription, RNA processing/export, translation and explanation. `genetics-model.js` owns transitions, required locations, complementary DNA/RNA windows, tRNA/codon pairing, release at stop and completion prerequisites. DNA synthesis on the opposite template is shown in reversed reading orientation. Primer setup, long extensions and parts of the molecular machinery are supplied by the model and disclosed. The cellular context is a nuclear eukaryotic gene. The product is explicitly a three-amino-acid fragment, not a complete functional protein.

Saved state uses `science-labs:{environment path}:genetic-information:v1`. Restore replays action history through the transition function, preserving corrections and refusing invented phase/completion flags. Written answers and optional identity are retained separately. Pointer drag, click/tap placement, keyboard controls and reduced-motion styling use the same state transitions. `genetics-workbench.js` defines physical work sites and component trays for every process. Targets sit on the DNA fork, primer, growing DNA/RNA end, promoter, RNA ends/intron, nuclear pore, and ribosome. `place` events record the component and site together; the model validates both before running a transition. Legacy tool/base events remain replayable. SVG animations show enzyme binding and extension, cap addition, intron removal/exon joining, tail growth, mRNA export, tRNA delivery/chain growth, and release at stop. Capping enzymes, spliceosome, and poly(A) polymerase are represented as machines; mRNA and tRNAs are labeled as RNA rather than enzymes. Animation/replay state is ephemeral and never adds student attempts; reduced motion shows the resulting structure immediately. The molecular view is brought into view for enzyme placement and action on smaller screens.

Report schema 2 shares one snapshot across PDF, native printing, and JSON: optional name/period, prediction, model results, evidence grouped by learning goal, concept checks, and verbatim written explanations. The visible report summarizes demonstrated work and concepts revisited after feedback. Raw action history is retained only in structured JSON and the embedded attachment for future assessment. Reports distinguish student-built excerpts from model-supplied work and do not infer mastery from completion alone. Human timestamps include a readable local date/time and time zone; the ISO timestamp is retained in the data. Named downloads and the print title include a sanitized student name when provided. Long writing flows across pages. Reports work offline after initial caching; no overall grade is assigned.

Student directions, feedback, checkpoints, glossary, and report labels use short sentences with ninth-grade explanations for new biology terms. The exported genetics report uses `schemaVersion: 2` and `activityVersion: 2`. The saved attempt uses storage `version: 1` and the existing `genetic-information:v1` key. Report and activity revisions describe the exported evidence, while the storage version identifies the replayable saved attempt. All molecular actions offer pointer dragging and a select-then-place alternative; the component tray and work sites stay together for touch use.

## Account platform for Amplify and Neon

`platform.html` / `src/platform/` implement the account portal independently of the standalone library. `vite.platform.config.js` outputs only the portal into `dist-platform/`. `server/` is a separately locked Node package for Express, Better Auth, PostgreSQL, Resend, optional Stripe, and the AWS Lambda adapter. Neon credentials and server secrets never enter the browser build. `infrastructure/template.yaml` defines the API Gateway/Lambda API and private versioned S3 runtime bucket; `amplify.yml` and `customHttp.yml` configure frontend hosting.

`scripts/build-platform.mjs` creates a content-hashed immutable runtime release containing all 16 full-lab pathways (15 catalog labs plus Sordaria), with explicit base-commit/dirty provenance. Upload/register precedes owner publication. Publication flags are stored separately for course, unit, and lab, with a selected release per lab. Existing assignments reference their original release. Unpublishing preserves already assigned access; disabling a release explicitly blocks it. Owner changes are recorded in publication history, with rollback for publication/version selection.

`server/src/access.js` enforces verified account, platform owner, teaching-workspace membership, class enrollment, and entitlement checks. Invitation tokens are hashed, expire, bind to a verified email, and can be redeemed once. Workspace trials and dated owner licenses support pilots; school membership enforces teacher seats. Stripe price choices are server-configured; signed raw-body webhooks update access transactionally, deduplicate events, and synchronize current subscription state. Manual licenses remain independent of billing updates. Billing is disabled by default.

The API serves public free-lab and authenticated runtime HTML/resources from private releases. Public requests use a separate publication/free-access gate before session middleware; private routes retain their verified-session and ownership checks. It injects a user/assignment context before the lab initializes. `runtime-bridge.js` scopes device keys to the user/assignment, hydrates the matching cloud draft, and registers the actual existing report getter. Shared/core/extended/osmosis reports and dedicated extraction/genetics reports retain their original controls and report structure. Cloud saves use revision checks; a stale save retains local work and asks for explicit conflict resolution. Submission stores an immutable report/state snapshot with a server receipt. The human-readable report sections are frozen with the assigned runtime, preserving its exact prompts and model limits. The teacher view/PDF adds the server receipt and separately recorded teacher review. Grading remains a separate teacher review. Each open runtime keeps its own in-memory draft so another tab cannot mix its state into that tab's report or backup. Original localStorage keys and standalone offline behavior are unchanged when no runtime context exists.

Authenticated runtime pages use no-store responses and no service worker; an open lab warms its PDF engine and can retain local work during a connection loss. Reopening assigned runtime pages offline is not yet supported. The standalone library has a device-work backup/export for explicit migration between origins. No automatic import or deletion of earlier student work occurs.

Local execution uses PGlite with the same PostgreSQL migrations and real Better Auth sessions. Email is captured in a loopback-only development outbox. Hosted execution uses Neon and Resend, with independent development/production databases, secrets, origins, and release buckets. Cookie login requires an intentional same-site domain setup; production is configured for prepdrawer.com with api.prepdrawer.com; development uses dev.prepdrawer.com with api.dev.prepdrawer.com. DNS and hosted acceptance remain separate deployment work. [Deployment and acceptance details](PLATFORM_DEPLOYMENT.md) distinguish local validation from actual hosted-service acceptance.

## Future localization contract — app and print

**Required future capability, not implemented by this documentation update:** students can choose Spanish or another available language in the app, and teachers can produce translated handouts and reports. The same design must support adding languages without duplicating scientific models or inventing new lab IDs. See [G18](LAB_DESIGN_GUIDE.md#g18) and AUD-10 for acceptance.

1. **Separate content identity from language.** Keep stable lab, unit, course, question, condition, answer-choice, assessment, and rubric IDs. Move authored display strings and structured instructional content into versioned locale-aware definitions, including diagrams, accessible labels, validation, feedback, and report prompts. Language codes such as `en` and `es` identify display content; they do not change the model, result, or content identity. Keep the translation-library/service choice open until implementation.
2. **Separate interface and output preferences.** Plan distinct app/interface, lab-content, report-output, and resource-output language choices where their coverage differs. A teacher's English interface must be able to request a Spanish worksheet. A student's explicit language selection takes priority over a browser hint. Remember guest/free preferences locally without requiring an account or trial. Keep numeric storage canonical while formatting and validating localized input unambiguously.
3. **Define real availability.** Track language coverage and draft/reviewed/published status per interface, lab release, report, and resource. Expose languages only for the coverage actually published, and explain missing-language fallback. A global Spanish interface must not imply every lab or private teacher question is translated. A translated resource follows the original course/unit/lab publication and entitlement rules; locale parameters must not bypass private or paid access.
4. **Preserve attempts and evidence.** A locale change updates presentation without restarting the simulation, changing its seed or answer order, clearing a response, altering correctness, or marking work complete. Store the rendered language and translation version alongside immutable release/report snapshots when implemented. Retain the original prompts and verbatim responses. Generate later translated report copies from the matching reviewed prompt version, label them, and keep the original submission intact. Future assessment uses stable IDs and must not assume all free-text answers are in English.
5. **Share definitions across app and documents.** Use matching reviewed localized content for app text, blank materials, completed PDFs, and native print. Keep required Unicode fonts, text layout, punctuation, scientific notation, and supported script/direction handling in the acceptance contract. Avoid permanently baking translatable labels into bitmap artwork. Package the necessary language assets with each immutable runtime; cache/local-PDF support follows the existing standalone versus platform offline contract.
6. **Use review and staff permissions.** Treat machine-assisted output as a translation draft, not a published language. Record scientific, language, reading-level, and visual/PDF review. Translation editing/review/publication should follow the staff permission pattern as those tools are implemented; metrics-viewing access must not grant content-editing rights. Do not add a public translation action that transmits student answers or silently rewrites teacher-authored material.

Publisher resource language/edition records in the curriculum dataset remain distinct from app and printable-material localization. A Spanish textbook record does not prove a Spanish lab, a translated PDF, approved alignment, or whole-course readiness. Plan separate implementation/review evidence before changing those statuses. No dataset counts, runtime schemas, API contracts, language assets, or publication settings change in this documentation-only update.
